KEYLOGGER is an educational Windows application developed in C++20 to explore low-level operating system interactions, event processing, keyboard input handling, and file-based logging. The project focuses on practical implementation of native Windows API functionality and the organization of a C++ application using a modular architecture. Its primary purpose is to demonstrate how a native application can communicate with the Windows operating system, retrieve information about active windows, process console input, manage system-wide hotkeys, and record application events. The software was developed as a practical programming exercise involving Windows internals, the C++ Standard Library, build automation, and version control.
The application continuously monitors the currently active foreground window and detects transitions between applications. Foreground window information is obtained using the GetForegroundWindow function, while GetWindowTextW retrieves the title associated with the selected window. Window titles are processed as Unicode strings and converted from UTF-16 to UTF-8 using WideCharToMultiByte to ensure consistent text representation in the application’s logging system. When a foreground window change is detected, the program records the corresponding event together with a timestamp. Event timestamps are generated using facilities provided by the C++ Standard Library. The application uses periodic polling to identify changes in window focus, allowing it to operate without requiring a graphical user interface or external dependencies beyond the Windows platform and the supported C++ runtime.
Keyboard input processing is implemented through the Microsoft C runtime functions _kbhit and _getwch. These functions allow the application to detect and retrieve keyboard input directed to its own console. The current implementation does not intercept arbitrary keyboard input from other applications and does not provide system-wide keystroke recording. Global keyboard interaction is limited to explicitly registered hotkeys implemented through the Windows API. The application registers the Ctrl + Shift + K combination using RegisterHotKey and processes the corresponding WM_HOTKEY message through PeekMessage. When the registered combination is detected, the main execution loop terminates, and the application releases the registered hotkey using UnregisterHotKey. This mechanism demonstrates the Windows message-handling model and provides controlled termination independently of the currently focused application.
The source code is organized into independent modules responsible for specific application functionality. The main.cpp file contains the application entry point and coordinates the primary execution loop. The Window module handles foreground window detection, title retrieval, and character encoding conversion. The Time module provides timestamp generation and formatting. The logger module implements file-based event recording using standard C++ file streams. The Hotkey module manages global hotkey registration, message processing, and resource cleanup. Each module separates function declarations from their implementations through dedicated header and source files. This structure improves code organization, reduces unnecessary dependencies between components, and provides a foundation for further development and maintenance.
The logging subsystem stores supported application events in a local text file named logs.txt, created relative to the process working directory. Events are written using append operations, allowing new records to be added without overwriting previously collected information. The recorded data includes foreground window transitions, event timestamps, and supported console input events. Log files are excluded from version control to prevent accidental publication of locally generated information. Since window titles and console input may contain sensitive information, generated logs should be reviewed before sharing or distributing them.
The application does not implement remote data transmission, credential extraction, persistence mechanisms, or concealed system-wide keyboard interception.
The project uses CMake as its primary build configuration system. The CMakeLists.txt file defines the application target, specifies C++20 as the required language standard, and includes the source files necessary to produce the executable. CMake version 3.20 or later is required. The application is designed for Microsoft Windows and requires a compatible C++ compiler with support for the Windows API and C++20. The project has been successfully configured and compiled using the Microsoft Visual C++ toolchain through MSBuild. A standard build can be performed from the project root directory by executing cmake -S . -B build, followed by cmake –build build. When using the Visual Studio generator with its default Debug configuration, the resulting executable is typically located at build/Debug/KEYLOGGER.exe. Alternative build configurations and generators may produce executables in different directories.
The current version represents a functional educational prototype rather than a production-ready monitoring solution. Its architecture is intentionally straightforward, emphasizing direct interaction with native operating system interfaces and the implementation of fundamental C++ programming concepts. Existing limitations include its dependency on the Windows operating system, console-based execution, periodic foreground window polling, and local plain-text logging. The project does not provide a graphical interface, centralized configuration management, or automated testing infrastructure. These limitations define the scope of the current implementation and provide opportunities for future architectural improvements.
KEYLOGGER was developed to consolidate practical knowledge of C++ programming, Windows API integration, system message processing, Unicode character handling, file operations, modular software design, CMake configuration, and Git-based version control. The project serves as a technical demonstration of native Windows application development and provides a foundation for further experimentation with operating system interfaces and event-driven programming. It is intended exclusively for educational purposes and controlled experimentation in authorized environments.
